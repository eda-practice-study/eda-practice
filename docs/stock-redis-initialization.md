# 초기 재고의 DB 저장과 Redis 반영

## 목표와 범위

`ProductCreated`를 소비하면 DB에 수량 0인 Stock과 처리 이력을 저장한다.
신규 Stock을 만든 경우에만 DB 커밋 이후 Redis에 초기 가용 재고를 추가한다.
Redis 장애 때문에 성공한 DB 저장을 롤백하거나 해당 이벤트를 Kafka에서 재시도하지 않는다.
DB 자체의 장애와 저장 실패에는 기존 재시도·DLT 정책을 적용한다.

프로젝트는 DB를 최종 기준으로 삼고, Redis는 조회와 주문 재고 차감 성능을 높이는 용도로 사용하려 한다.
이번 변경은 초기 재고 생성만 다룬다. 조회 시 캐시 복구, 재고 증가·차감, 예약 내역 복원은 구현하지 않는다.

## 처리 순서와 핵심 결정

```text
ProductEventListener
  → StockService.createFor(messageId, productId)
      → 처리 이력 확인
      → 미처리 메시지의 이력 저장
      → 신규 상품이면 Stock(quantity=0) 저장
      → DB 트랜잭션 커밋
  → 신규 Stock을 만든 경우 StockCache.initialize(productId)
      → SET stock:available:{productId} 0 NX
      → Redis 실패는 로그로 기록하고 반환
  → 리스너 정상 반환
  → 기존 BATCH ACK 정책으로 오프셋 커밋
```

키 표기의 `{productId}`는 설명용 자리표시자다. 실제 키 예시는 `stock:available:42`다.

| 결정 | 이유와 동작 |
|---|---|
| DB 커밋 후 Redis 호출 | 별도 서비스 빈의 `@Transactional` 메서드를 리스너에서 동기 호출한다. 트랜잭션 프록시의 커밋까지 성공해야 호출이 반환된다. 리스너 자체에는 트랜잭션을 붙이지 않는다. |
| 서비스가 신규 생성 여부 반환 | 새 Stock을 만들면 `true`, 이미 처리한 메시지이거나 Stock이 있으면 `false`다. 기존 Stock을 과거 생성 이벤트로 초기화하지 않는다. |
| Redis 처리를 별도 `StockCache`로 분리 | DB 트랜잭션을 Redis 접근으로 연장하지 않고 Redis 접근 실패 처리의 범위를 제한한다. |
| 문자열 수량과 `SET NX` 사용 | `StringRedisTemplate.opsForValue().setIfAbsent()`로 값이 없을 때만 `"0"`을 기록한다. 사전 조회 후 SET하는 방식 대신 한 명령으로 기존 키 덮어쓰기를 막는다. |
| TTL 미설정 | 초기화 시 자동 만료를 예약하지 않는다. 향후 주문 차감 수량을 보관할 수 있으므로 만료 후 DB 수량으로 단순 복원해도 안전하다고 가정하지 않는다. |
| Redis 접근 예외는 로그 후 정상 반환 | `DataAccessException`을 처리한다. DB 오류와 메시지 형식 오류는 이 처리 범위에 포함하지 않는다. Redis 실패만으로 DLT에 보내지 않는다. |
| 연결·명령 타임아웃 각각 500ms | Redis 장애가 Kafka 소비 스레드를 오래 지연시키는 것을 줄인다. 두 설정은 전체 처리 시간 500ms를 보장하는 제한은 아니다. |

처리 이력은 **DB 재고 생성 처리가 끝났음**을 나타낸다. Redis 반영 성공까지 보장하는 이력이 아니다.
Redis가 이미 존재하는 키를 거절하면 정상적으로 반환하며, 기존 값이 DB와 같은지 검증하거나 수정하지 않는다.

## 실패 시 결과

| 상황 | DB·처리 이력 | Redis | Kafka |
|---|---|---|---|
| 신규 생성 성공 | 함께 커밋 | 키가 없으면 0 추가 | 정상 완료 |
| DB 저장·커밋 실패 | 함께 롤백 | 호출하지 않음 | 기존 재시도·DLT 정책 |
| Redis 쓰기 실패 | 커밋 유지 | 키가 없거나 결과를 확신할 수 없음 | 정상 완료, Redis 때문에 재시도하지 않음 |
| DB 커밋 직후 프로세스 종료 | 커밋 유지 | 초기화되지 않았을 수 있음 | 재수신돼도 처리 이력으로 건너뛰며 Redis를 복구하지 않음 |
| Redis 성공 후 오프셋 커밋 전 종료 | 커밋 유지 | 초기화된 값 유지 | 재수신돼도 Redis를 다시 초기화하지 않음 |
| 새 메시지 ID로 기존 상품 수신 | 새 이력만 커밋, 재고 보존 | 호출하지 않음 | 정상 완료 |

## 감수한 위험

1. **Redis 초기화 유실을 자동 복구하지 않는다.** DB 커밋과 Redis 쓰기는 원자적이지 않다.
   둘 사이의 프로세스 종료나 Redis 장애로 키가 없는 상태가 남을 수 있다.
   처리 이력이 이미 커밋되므로 이벤트 재전송만으로는 복구되지 않는다.
   자동 재시도 큐나 Redis 갱신용 Outbox는 이번에 추가하지 않는다.
2. **기존 키를 보존하는 것이 최신 수량을 보장하지는 않는다.** `SET NX`는 기존 값 덮어쓰기를 막지만,
   그 값이 잘못되었거나 오래되었어도 그대로 유지한다. TTL도 없어 별도 조치 전까지 불일치가 지속될 수 있다.
3. **늦은 초기화와 재고 변경의 경합이 남는다.** DB에 재고를 생성한 뒤 Redis 초기화가 지연되는 사이,
   다른 요청이 DB 재고를 증가시키고 Redis 반영에 실패하면 이후 초기화가 빈 키에 오래된 0을 기록할 수 있다.
   재고 증가·차감 기능을 추가할 때 초기화와 변경을 함께 조정하는 버전·직렬화·복구 정책이 필요하다.
4. **Redis 유실과 주문 예약 유실은 다르다.** 향후 Redis에서 먼저 차감하고 DB에 나중에 반영한다면,
   미반영 차감이 Redis에만 있는 구간은 DB 수량만으로 정확히 복원할 수 없다.
   DB 수량을 그대로 복사하면 이미 예약한 수량이 다시 판매 가능해질 수 있다.
   예약을 영속화할지, 미반영 차감의 유실을 허용할지 주문 기능에서 결정해야 한다.
5. **Redis 장애는 관측하고 후속 복구해야 한다.** 초기화 실패는 상품 ID와 예외를 로그로 남기지만
   별도의 영속 복구 작업이나 실패 지표를 생성하지 않는다. 후속 요청에서 복구하는 기능이 생기기 전까지는
   키가 계속 없을 수 있다. Redis 재시작·퇴거·수동 삭제도 같은 누락 상태를 만들 수 있다.
6. **소비 지연은 완전히 제거되지 않는다.** Redis는 DB 커밋 이후에도 동기로 호출하므로
   타임아웃이 발생하는 동안 Kafka 소비는 기다린다. DB 트랜잭션은 이미 종료되었지만 오프셋 커밋은 늦어진다.

향후 캐시 미스 복구에서는 당시 DB 재고와 미반영 예약을 함께 고려해야 한다.
기존 키가 있으나 잘못된 경우의 대사·보정 정책도 캐시 미스 복구와 별도로 필요하다.

## 검증

- 단위 테스트: 서비스 반환값, 신규 생성 후 Redis 호출 순서, 중복·DB 실패 시 미호출,
  Redis 연결 실패의 예외 격리를 검증한다. 각 테스트의 검증은 해당 테스트 안에 직접 둔다.
- 통합 테스트: Embedded Kafka와 실제 Valkey 컨테이너로 초기값 0, TTL 없음, 기존 값 보존,
  DB 커밋 이후 Redis 호출, 키 유실 후 중복 이벤트의 미복구를 검증한다.
- Redis 오류를 주입해도 DB·처리 이력과 Kafka 오프셋이 커밋되고 Kafka 재시도·DLT가 발생하지 않는지 검증한다.
- 기존 PostgreSQL의 롤백·동시 처리 테스트와 product·stock 회귀 테스트를 실행한다.

실행 명령: `./gradlew :stock:test :product:test`.
통합 테스트에는 Docker가 필요하다. 개발 환경의 `SPRING_DATA_REDIS_HOST` 설정을 그대로 사용하며,
별도 환경에서는 Spring Redis host·port 설정으로 연결 대상을 지정한다.
