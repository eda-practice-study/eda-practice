# 0002 처리 이력과 업무 데이터를 같은 트랜잭션에 저장한다

- 상태: 채택
- 적용 범위: stock, order
- 기록일: 2026-11-07

## 배경과 대안

Outbox 재발행이나 오프셋 커밋 전 종료로 같은 메시지를 다시 받을 수 있다.
이력을 메모리나 Redis에만 두면 재시작과 유실을 고려해야 한다.
이력과 업무 저장의 트랜잭션을 분리하면 성공하지 않은 처리를 완료로 기록할 수 있다.

## 결정

각 서비스의 `processed_message`에 입력 messageId를 UUID PK로 저장한다.
업무 데이터와 후속 Outbox까지 같은 DB 트랜잭션에 포함한다.
먼저 이력을 조회하고, 동시 처리의 마지막 방어는 PK와 업무 테이블의 상품 ID 유일 제약에 맡긴다.
충돌한 트랜잭션은 롤백하고 새 트랜잭션에서 재시도한다. 실패한 트랜잭션 안에서 예외를 삼키고 계속 처리하지 않는다.
할당 UUID가 기존 행을 merge하지 않도록 처리 이력 엔티티는 `Persistable`로 신규 여부를 제공한다.

## 감수한 위험

조회만으로 경쟁을 막지는 못하므로 정상적인 중복 경쟁도 DB 예외와 재시도를 거칠 수 있다.
현재는 서비스마다 해당 처리 이력을 사용하는 하나의 업무 소비 흐름이 있다.
서로 독립적인 여러 핸들러가 같은 테이블을 공유하게 되면 consumer 식별자를 포함하는 키를 검토해야 한다.
이력 정리 정책이 없으며, 이력을 지운 후의 과거 메시지 재처리도 별도 고려가 필요하다.
처리 이력은 DB 업무 처리의 완료를 의미한다. Redis 반영이나 Kafka 후속 소비 완료를 의미하지 않는다.

적용 동작은 [재고](../domains/stock.md)와 [스냅샷](../domains/order.md),
검증은 각 도메인 문서가 연결한 DB 통합 테스트를 참조한다.
