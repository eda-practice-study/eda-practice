# Outbox 도입 후에도 남는 문제

Outbox는 **이벤트 유실**을 해결했다. 그 대가로 새로 생긴 문제와, 여전히 남은 문제를 정리한다.

## 1주차 문제의 처리 현황

| 항목 | 상태 |
|------|------|
| `A-1. 이벤트 유실` | **해결.** 커밋되면 이벤트 레코드가 반드시 남고, 발행 실패 시 `PENDING` 으로 유지돼 다음 주기에 재시도된다 |
| `A-2. 중복 소비` | 미해결. at-least-once는 그대로이고 Outbox가 발행 쪽 중복을 오히려 늘렸다 → A-1, A-2 |
| `A-3. 컨슈머 무한 재시도` | 미해결. 발행 쪽에도 같은 구조의 문제가 생겼다 → D-1 |
| `B-1. 최종적 일관성 지연` | 미해결. 폴링 주기만큼 오히려 늘었다 → B-1 |
| `B-2. Stock 생성 실패 보상 없음` | 미해결 |
| `C-1. 재고 등록 Lost Update` | 미해결. 3주차 과제 |

---

## A. 중복 발행

같은 이벤트가 Kafka에 두 번 이상 들어갈 수 있다. **stock 쪽 방어는 이미 되어 있다** — `existsByProductId` 로 걸러내고 `product_id` unique 제약이 최종 보증을 한다. 문제는 중복이 발생한다는 사실 자체다.

### A-1. 발행 성공과 상태 저장 사이의 창

- **증상** 같은 이벤트가 두 번 발행됨
- **원인** `send()` 성공을 확인한 직후 `UPDATE status='PUBLISHED'` 전에 프로세스가 죽으면, 레코드가 `PENDING` 으로 남아 다음 주기에 다시 발행된다

```
send() ✓ ─── [이 사이에 죽으면] ─── UPDATE status='PUBLISHED'
                                     ↑ 여기 도달 못 하면 재발행
```

- **왜 못 없애나** DB 커밋과 Kafka 발행은 서로 다른 저장소라 원자적으로 묶을 수 없다. Outbox는 이 창을 **저장 시점**에서 없앤 것이고, **발행 시점**의 창은 구조적으로 남는다
- **대응** 컨슈머 멱등성으로 흡수한다. at-least-once를 전제로 두는 것이 정공법이다

### A-2. 다중 인스턴스의 동시 조회

- **증상** product 인스턴스를 2대 이상 띄우면 같은 이벤트가 인스턴스 수만큼 발행됨
- **원인** 조회에 잠금이 없다. 두 인스턴스가 같은 `PENDING` 100건을 함께 집는다

```
인스턴스 A ─► SELECT ... PENDING ─► [1,2,3] 발행
인스턴스 B ─► SELECT ... PENDING ─► [1,2,3] 발행   ← 같은 것
```

- **왜 잠금이 없나** `FOR UPDATE SKIP LOCKED` 는 트랜잭션이 있어야 락이 유지된다. 릴레이를 트랜잭션 없이 돌리기로 한 결정([01-implementation.md](01-implementation.md) 설계 결정 3)의 대가다
- **대응** 지금은 단일 인스턴스 전제. 확장 시 선택지는 셋이다
  - 조회 트랜잭션 + `FOR UPDATE SKIP LOCKED` — 트랜잭션 없음의 이점을 포기
  - 상태를 `IN_PROGRESS` 로 선점 후 커밋 — 선점 후 죽으면 stuck 레코드 회수 로직 필요
  - ShedLock 등으로 스케줄러를 클러스터에서 1대만 실행 — 처리량은 늘지 않음

## B. 발행 지연

### B-1. 폴링 주기만큼의 지연

- **증상** 상품 생성 후 재고 row가 생기기까지 최대 `폴링 주기 + 발행 + 컨슈머 처리` 만큼 걸린다
- **원인** 릴레이가 `fixedDelay=1000` 으로 돌아, 커밋 직후 발행되는 경우와 1초 뒤 발행되는 경우가 있다

```
1주차:  커밋 ─► 즉시 send            (유실 위험 있음)
2주차:  커밋 ─► 최대 1초 대기 ─► send  (유실 없음)
```

**유실을 막는 대가로 지연을 받아들인 것이다.** 1주차에는 지연이 없었지만 이벤트가 사라질 수 있었다.

- **대응** 주기를 줄이면 지연은 줄지만 빈 조회 쿼리가 늘어난다. 근본적으로는 CDC(Debezium)로 WAL을 구독하면 수십 ms로 줄어든다 — 대신 Kafka Connect 인프라와 `wal_level=logical` 설정이 필요하고, "미발행 조회 / 발행 표시" 개념 자체가 사라진다

### B-2. 재고 등록 404 타이밍

- **증상** 상품을 만든 직후 `POST /admin/stocks` 를 호출하면 `404 UNKNOWN_PRODUCT`. 1~2초 뒤에는 성공한다
- **원인** B-1의 지연 + 컨슈머 처리 시간. 정상 동작인데 사용자에겐 버그로 보인다
- **왜 2주차에 안 고치나** 이건 전파 지연이 아니라 **API 설계** 문제다. 재고 준비 상태를 조회할 수단이 없는 것이 원인이다
- **대응** 선택지
  - 재고 준비 여부 조회 API + 어드민 UI 폴링
  - `POST /admin/stocks` 가 재고 row가 없을 때 `409 Conflict` + `Retry-After` 를 주어 "아직 준비 중"과 "존재하지 않는 상품"을 구분
  - 상품 생성 응답에 재고 준비 예상 시각을 포함

## C. 이벤트 순서

### C-1. 파티션 간 순서는 보장되지 않는다

- **현재 보장 범위** 메시지 키가 `aggregate_id`(= productId)이므로 **같은 상품의 이벤트는 같은 파티션**으로 가고, 컨슈머 그룹 내에서 한 파티션은 한 컨슈머만 처리한다. 따라서 상품 단위 순서는 지켜진다
- **보장되지 않는 것** 서로 다른 상품 이벤트 간의 전역 순서. 파티션이 4개라 상품 A의 이벤트가 상품 B보다 먼저 발행됐어도 늦게 소비될 수 있다
- **평가** 상품 간 순서에 의미가 없으므로 지금은 문제가 아니다. 주문·결제가 들어오면 애그리거트 경계를 넘는 순서 요구가 생길 수 있다

### C-2. 재시도가 섞이면 순서가 흔들린다

- **증상** 발행 실패 후 재시도하는 사이 뒤 이벤트가 먼저 나갈 수 있다
- **현재 대응** 실패 시 그 자리에서 **중단**해 뒤 이벤트를 건드리지 않는다. 다음 주기에 실패한 건부터 다시 시도하므로 id 순서가 유지된다
- **남는 구멍** A-2(다중 인스턴스)에서는 이 보장이 깨진다. 두 인스턴스가 같은 목록을 집으면 발행 순서를 제어할 수 없다

## D. 운영

### D-1. Poison message가 뒤 이벤트를 막는다

- **증상** 특정 레코드에서 계속 실패하면 그 뒤 이벤트가 전부 밀려 영영 발행되지 않는다
- **원인** 순서를 지키려고 실패 시 중단하기 때문이다. 1주차 `A-3. 컨슈머 무한 재시도` 와 같은 구조가 **발행 쪽에** 생겼다

```
[1 ✓] [2 ✓] [3 ✗ 영구 실패] [4 대기] [5 대기] ...
                 └── 매 주기 3번에서 멈춤
```

- **대응** 없음. 재시도 횟수 제한과 DLQ가 5주차 과제다. 그때 `OutboxStatus.FAILED` + `retry_count` 를 추가해 한계를 넘은 레코드를 건너뛰고 DLQ로 보낸다 (상태 모델을 enum으로 둔 이유)

### D-1-1. 브로커 장애 시 릴레이가 통째로 느려진다

- **증상** Kafka가 죽으면 실패한 이벤트뿐 아니라 **모든 발행이** `max.block.ms` 만큼 지연된다
- **원인** `send()` 는 브로커 메타데이터를 못 얻으면 그 자리에서 블로킹된다. 릴레이가 단일 스레드라 그동안 아무것도 못 한다
- **현재 대응** `max.block.ms=5000` 으로 낮춰 재시도 간격을 60초에서 약 6초로 줄였다. 근본 해결은 아니다
- **남는 문제** 브로커가 오래 죽어 있으면 `PENDING` 이 계속 쌓이고, 복구 후 한 번에 몰려 나간다. 배치가 100건이라 적체가 크면 해소에 여러 주기가 걸린다

### D-2. outbox 테이블이 무한히 커진다

- **증상** 발행 완료된 레코드가 계속 쌓인다
- **원인** 기록 차원에서 삭제하지 않기로 했다 (과제 요구)
- **영향** `status='PENDING'` 조회가 전체 스캔이 되면 폴링마다 비용이 커진다. 지금은 데이터가 적어 드러나지 않는다
- **대응** 선택지
  - `status` 부분 인덱스 (`WHERE status = 'PENDING'`)
  - 일정 기간이 지난 `PUBLISHED` 레코드를 별도 테이블로 아카이빙
  - 파티셔닝 후 오래된 파티션 분리

### D-3. 릴레이가 멈춘 것을 알 수 없다

- **증상** 스케줄러 스레드가 죽거나 예외로 막히면 이벤트가 조용히 쌓인다
- **원인** `PENDING` 적체를 감시하는 장치가 없다
- **대응** 6주차 관측 과제. `PENDING` 개수와 가장 오래된 `PENDING` 의 나이를 메트릭으로 노출하는 것이 최소선이다

## E. 남은 구조적 문제

### E-1. Stock 생성 실패에 대한 보상이 없다

1주차 `B-2` 그대로다. Outbox는 이벤트가 **전달**되는 것까지만 보장한다. stock이 이벤트를 받고도 처리에 계속 실패하면 Product만 존재하는 상태가 유지되며, 되돌리는 장치가 없다.

### E-2. outbox 코드를 다른 서비스와 공유할 수 없다

3주차 이후 order·payment도 이벤트를 발행하므로 outbox가 서비스마다 필요해진다. 지금 코드는 product 모듈 안에 있어 그대로 재사용할 수 없다.

`common` 으로 올리는 것도 간단하지 않다 — `03-architecture.md` 는 *"common엔 공유 계약만, 도메인 로직 금지"* 로 정해두었고, outbox 엔티티와 릴레이는 계약이 아니라 메커니즘이다. `OutboxEvent` 가 product 도메인에 의존하지 않게(`aggregate_type` / `aggregate_id` 를 문자열로) 설계해둔 것은 나중에 뽑아내기 쉽게 하기 위한 것이다.
